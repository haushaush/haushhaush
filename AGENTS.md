# Architecture Rules

Subdirectories may have their own `AGENTS.md` (e.g. `supabase/functions/`); read it before changing files there.

- Homepage cards use session-scoped clients/projects, deadline-ranked projects and latest client/project contract end. Why: actionable work.

- Navigation changes keep routes and per-page permission checks. Why: no broken links.
- Meta token: resolve via `_shared/meta-config.ts` (secret only); billing functions use `META_BILLING_ACCESS_TOKEN`. Why: one resolver.
- Bonus: `bonus-berechnung` owns scoring, tiers and the exact call rows supplied to tiles/lists; frontend presentation helpers only calculate pacing and labelled forecasts. Completeness stays separate; approval uses a locked version-checked RPC requiring audited acknowledgement. Why: honest progress without changing payroll or divergent call lists.
- Bonus customer base: Close is the source of truth for customers, Qonto for payments. `bonus-kunden-sync` mirrors Close leads with client status (hourly) into `bonus_kunden_aktuell`, links each lead once to a client (stored link → exact name → create; manual relink sticks), writes `clients.kundenstatus` only from Close and downgrades every CRM-betreut client without a betreut Close lead on each run (logged in `bonus_sync_log.details`); all bonus syncs use only the Haush-Haush Close key with no fallback account, and grows the current month's snapshot from counted rows. `bonus-checkins-sync` resolves checkins only via that list; checkins on non-client leads go to `bonus_checkin_kandidaten` and never count until promoted. `bonus-churn-sync` is the only automated writer of Close-sourced `bonus_churn_events` (insert-only). Why: the CRM must mirror Close, and only humans may turn a lead into a counted customer.
- Close mirror: `bonus-kunden-sync` mirrors every Haush-Haush Close lead (all statuses, never deletes) into `close_lead_spiegel` incrementally via status-change activities with one daily full pass; only betreut statuses feed `bonus_kunden_aktuell`. `close-abschluesse-sync` is the only writer of `close_abschluesse` (Sales pipeline) and `kunden_laufzeit_stand`, derives runtimes only from won deals (never estimates), our Close first and read-only Viral Connect deals (`close_opportunities`, fields resolved by exact name via `close_vc_feldkatalog`) as fallback; nothing is ever written to the Viral Connect account, writes them to `clients` and one-way to Notion. Why: Close → CRM → Notion in one direction, with no second source.
- Runtime edits: the Laufzeiten page writes only to Close via admin-only `close-abschluss-schreiben` (one customer per action, filled fields only; package only updated on an existing LS Cash Collect activity, never created; creation of a won Sales deal requires explicit confirmation), logs every attempt in `close_abschluss_schreiblog`, Verlängern (Upsell fields define contract end) and Beenden (opp → lead → note; abort on step 1, report partial success, no retry) use the same function, then re-reads the deal from Close; deal mapping and runtime derivation live in `_shared/closeAbschluesse.ts`. Why: Close stays the single source, the CRM is only an input mask.
- Sales overview headline KPIs come only from the n8n-filled s-kpi Google Sheet, mirrored hourly by `sales-sheet-sync` (full import on first successful run, then last 14 days; idempotent upserts on natural keys; undated rows counted, not dropped); `sales-kpi-ingest` stays as a fallback that refuses writes unless `app_settings.sales_kpi_quelle` = "ingest". Why: the overview must match the daily Slack report exactly, from one source at a time.

- Project resets share the active Close source with runtimes, use signed previews and one atomic RPC, archive rather than delete, and exclude archived projects from operational reads. Why: preserve history and prevent partial resets.
- Customer links: `src/lib/kundenVerknuepfungen.ts` is the single source for per-system link status, suggestions (always with match reason, never auto-linked) and link/unlink writes; searches read full object lists, never link tables; dismissals in `kunde_link_vorschlag_verworfen`. Slack and Pipedrive are NOT linked at customer level (system-wide tools) — never add them back to `SYSTEME`. Why: detail tab, empty-state tiles and the review page must agree.
- Ad-budget mapping: `werbebudget_zuordnung` maps a customer to a whole campaign or to adsets of a shared campaign on our own Meta accounts (one owner per object, campaign-or-adsets enforced by trigger, never auto-set); edited only in the customer Verknüpfungen tab, Finanzen lists unassigned campaigns read-only. Why: spend per customer must be attributable without splitting or estimating.
- Credentials come from secrets; `integration_settings` holds non-secret state. Why: no secrets in tables.
- Bookkeeping: one source per customer via Close "Marke" → `buchhaltung_quelle`; unknown = ungeklärt, never default or add both; lexoffice read-only. Why: two companies.
- Finance invoices: `src/lib/rechnungen.ts` alone maps Qonto/lexoffice invoice fields and statuses (unknown → "sonstige", shown raw). Why: consistency.
