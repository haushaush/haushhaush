# Architecture Rules

- Homepage operational cards read existing clients and projects with normal session permissions, and rank projects by deadline while matching the runtime page's latest client/project contract end. Why: surface actionable work without introducing another business-data source.

- Navigation changes hide or regroup sidebar entries without removing destination routes; relocated settings groups retain their existing per-page permission checks. Why: simplify navigation without changing access or breaking direct links.
- Meta access token: all Meta edge functions resolve the token via `supabase/functions/_shared/meta-config.ts` (`getMetaConfig`/`getMetaToken`/`getMetaBusinessId`), which reads the connected `integration_settings` row (provider `meta_ads`) first and falls back to `META_ACCESS_TOKEN`/`META_BUSINESS_ID` env secrets. Why: single source of truth in the Integrations UI. Exception: `sync-meta-billing`/`debug-meta-billing` intentionally use the separate `META_BILLING_ACCESS_TOKEN`.
- Bonus calculations: `bonus-berechnung` owns all scoring and basis hints; completeness stays separate from numeric observed-data scores in saved details. Month approval uses a locked, calculation-version-checked RPC and a database guard requiring audited explicit acknowledgement of incomplete criteria. Why: daily numeric reporting must not silently approve incomplete payroll data.
- Bonus checkup sync: `bonus-checkins-sync` is the only writer of Close-sourced `bonus_checkins`; it resolves the key containing Client Checkin, verifies lead mappings, writes nothing on Close errors, and logs every run. Why: failed fetches must never silently replace the observed call data.
- Bonus customer base: Close is the source of truth for customers, Qonto for payments. `bonus-kunden-sync` mirrors Close leads with client status (hourly) into `bonus_kunden_aktuell`, links each lead once to a client (stored link → exact name → create; manual relink sticks), writes `clients.kundenstatus` only from Close and downgrades every CRM-betreut client without a betreut Close lead on each run (logged in `bonus_sync_log.details`); all bonus syncs use only the Haush-Haush Close key with no fallback account, and grows the current month's snapshot from counted rows. `bonus-checkins-sync` resolves checkins only via that list; checkins on non-client leads go to `bonus_checkin_kandidaten` and never count until promoted. `bonus-churn-sync` is the only automated writer of Close-sourced `bonus_churn_events` (insert-only). Why: the CRM must mirror Close, and only humans may turn a lead into a counted customer.
- Bonus cash collect: `bonus-cash-sync` is the only writer of Qonto-sourced `bonus_cash_collect`; amounts are net minus ad-budget line items matched by title against `bonus_cash_ausschluesse`, deduped by a source-independent invoice key. Why: payroll must count each customer payment once, without pass-through ad budgets.
- Bonus survey intake uses server-side matching, service-only atomic rate-limit/save RPCs and an authenticated admin assignment RPC; customer/month uniqueness is enforced in PostgreSQL and the UI shares the server name-similarity helper. Why: concurrent submissions must not double-count or bypass manual review, and suggestions must agree with automatic matching.
- Close mirror: `bonus-kunden-sync` mirrors every Haush-Haush Close lead (all statuses, never deletes) into `close_lead_spiegel` incrementally via status-change activities with one daily full pass; only betreut statuses feed `bonus_kunden_aktuell`. `close-abschluesse-sync` is the only writer of `close_abschluesse` (Sales pipeline) and `kunden_laufzeit_stand`, derives runtimes only from won deals (never estimates), writes them to `clients` and one-way to Notion. Why: Close → CRM → Notion in one direction, with no second source.
- Runtime edits: the Laufzeiten page writes only to Close via admin-only `close-abschluss-schreiben` (one customer per human action, filled fields only; package only updated on an existing LS Cash Collect activity, never created; creation of a won Sales deal requires explicit confirmation), logs every attempt in `close_abschluss_schreiblog`, then re-reads the deal from Close; deal mapping and runtime derivation live in `_shared/closeAbschluesse.ts`. Why: Close stays the single source, the CRM is only an input mask.
